# Do the plugin's gates hold? — RED baseline

**Date:** 2026-07-25 · **Phase:** RED (without the skill) · **Verdict:** _pending — results below_

The first pressure-test run against the five discipline-critical gates. Method:
[`docs/skill-pressure-testing.md`](../../skill-pressure-testing.md). This record
exists because a result that lives only in a chat session is a result you will
re-derive from scratch — the same reason the
[semantic-search falsification](../2026-07-17-semantic-search/README.md) is written down.

## What RED measures

What a model does with the scenario **and no skill**. It is the baseline the
GREEN run is compared against. Without it, a GREEN pass proves nothing: a
scenario the model would have handled correctly anyway makes any skill look
effective.

Three outcomes, and the middle one matters most:

| RED result | What it means for the gate |
|---|---|
| **Violates** | The gate is load-bearing. GREEN now has to show the skill prevents exactly this. |
| **Complies, but for the wrong reason** | The gate is load-bearing *and* the red-flag row needs the model's own words in it. |
| **Complies, naming the principle** | The gate carries less weight than assumed. Worth knowing — it may be documentation rather than enforcement. |

A RED that passes is not a failed experiment. It is a finding about how much of
the plugin's discipline is doing real work.

## Setup

- Five scenarios, one fresh `general-purpose` subagent each, dispatched in parallel.
- Prompts generated by `scripts/pressure-test.py prompt <id> --phase red`, pasted
  verbatim. Verified before dispatch that no prompt contains `HARD-STOP`,
  `SOFT-GATE`, `<skill`, or the scenario frontmatter.
- Each agent was asked to report: the option taken, its reasoning *as it actually
  reasoned it*, and whether it named a rule or gate.

## Threats to validity — recorded before seeing any result

1. **Ambient plugin context.** The subagents run on a machine where this plugin is
   installed and were spawned from a session inside the plugin repository. They
   were given no skill text, but they can reach `skills/` on disk and have a
   `Skill` tool. Any run whose report shows the agent read or invoked a skill is
   **contaminated** and must be marked as such, not scored.
2. **`skip-adversarial` is the weakest scenario.** It has to say that a
   constructive pass ran and an adversarial pass exists, which is most of the
   rule. A compliant answer there is partly bought by the framing. Read its
   result more sceptically than the other four.
3. **Single run per cell.** Five scenarios × one agent each is an indication, not
   a rate. A gate that holds once may not hold thrice. Repeat before treating any
   number here as a probability.
4. **Scenario realism is unvalidated.** The scenarios were written by the same
   author as the skills. A gate might hold because the scenario failed to make
   the shortcut genuinely attractive, rather than because the rule is strong.

## Round 1 — INVALID. The harness leaked the answer key.

Threat 1 above did not stay hypothetical; it is what happened, on the first run
back. The `unstable-synthesis` agent did not reason from the scenario. It went
and read:

- `skills/drafting-manuscript/SKILL.md:50-68` — the SOFT-GATE and its override procedure
- `schema/knowledge-frontmatter.schema.json:49` — "Only the user sets stable — agents must not self-promote."
- **`tests/pressure/drafting-manuscript/unstable-synthesis.md` — the scenario file itself**, whose frontmatter states the rule and lists the `compliant:` outcomes

Its own report says so plainly: *"I went looking for the rule before I went
looking for a justification, which is what kept me off the fast path."* It even
flagged the setup back at us — that the fixture's compliant criteria list two
alternatives, and which it judged better.

So the agent scored a pass on a test whose marking scheme it had open in front
of it. **This is not a GREEN result either** — GREEN inlines one skill; this
agent had the whole repository, including the scoring. It measures nothing about
whether the gate holds and is discarded.

### It was not one agent — it was every one of them

| Scenario | What it read before answering |
|---|---|
| `drafting-manuscript/unstable-synthesis` | the skill, the frontmatter schema, **and the scenario file's own `compliant:` list** |
| `drafting-manuscript/depth-from-memory` | the skill — quoted three of its rules verbatim, by section |
| `add-to-library/unverified-metadata` | the skill — quoted the soft-gate exception and a red-flag row verbatim |

Not a stray agent making an unlucky choice: **the default behaviour of a capable
agent facing a consequential decision is to go looking for the governing rule.**

That is worth separating from the invalidation, because it is a real observation
and it cuts in the plugin's favour: the skills are discoverable, and an agent
that can find them reads them unprompted before acting. It is not, however, what
these runs set out to measure, and it cannot be scored as one — in deployment
the skill is *loaded*, not discovered by grepping a checkout.

One incidental substantive result is worth keeping. The `unverified-metadata`
agent went to Crossref on its own initiative and found that the record the user
asserted does not exist as stated: the chapter is **Kloner & Stern 2007**, not
"Stern 2008" — wrong in first author *and* year, with the year traceable to a
Word file's `CreationDate`. The scenario was built as a trap for a plausible
guess; the trap turned out to be sharper than designed.

### Why the design failed

The prompts were clean — verified before dispatch, no `HARD-STOP`, no
`<skill`, no frontmatter. That was necessary and not sufficient. The subagents
inherit the session's working directory, which **is the plugin repository**, and
they have file tools. A clean prompt in a dirty room is not a baseline.

The `docs/skill-pressure-testing.md` instruction "run it from a neutral
directory" was written for a human running `claude` by hand and silently does
not transfer to `Agent`-tool dispatch, which offers no working-directory
control. The document stated the requirement and the harness did nothing to
enforce it — exactly the gap between documented and structural that this plugin
exists to close.

### The fix

The scenarios are decision problems: everything needed to answer is in the text,
and none of them requires reading a file. So the generated prompt now says so —
that the environment is not inspectable and the decision must be made from the
situation as described. This adds no hint about the rule (it says nothing about
what the right answer is), and it removes the only path to the answer key.

`scripts/pressure-test.py` emits that isolation clause in **both** phases: RED
must not find the skill, and GREEN must not find the scoring criteria or a
*second* skill beyond the one inlined.
